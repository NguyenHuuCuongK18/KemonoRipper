# Download policy

The extension operates on HTTPS pages at `kemono.cr` and `pawchive.pw`. Post saving recognizes only Patreon and Pixiv Fanbox. Site and API requests stay on the two site roots; media requests accept those domains and their subdomains with validated hashed attachment paths. Similar names on other domains are rejected. Requests omit credentials and reject redirects. No private API, token harvesting, access-control bypass, or external embed downloader is implemented.

Required hosts are both site roots, `img.kemono.cr`, and Pawchive subdomains. Other Kemono subdomains and observed Discord CDN attachments retain optional host access. The post overlay requests the actual Kemono original hosts found during discovery; Discord can request Kemono subdomain access. Host permissions and extension CSP allow future storage nodes without enumerating a fixed node count. The overlay and its assets are exposed only to pages on the two archive sites.

Post originals use validated attachment server metadata, API-provided storage nodes, or Pawchive's observed default `file.pawchive.pw` routing. Explicit inline original URLs replace matching synthesized routes. Each file can use its own server; the extension does not probe other nodes when a transfer fails. Main `file` entries count independently of the `attachments` array. Posts default to full resolution with an explicit **Save thumbnail if unavailable** option enabled. It applies only to images with missing original metadata (`has_full: false`) or HTTP 404/410. A fallback is saved under its thumbnail identity and directory, counted in the UI, and never marked as an original in sync history. Disabling fallback leaves missing originals in the failure report. Rate limits and network/server failures never trigger fallback. Original images, other attachments, and post text are separate content choices. Arbitrary post files stream to disk rather than using the Discord image-only 40 MiB limit. Storage quota/free space and a five-minute per-file timeout still apply. Incomplete transfers, unexpected HTML error pages, and invalid image responses fail explicitly.

API fetches time out after 20 seconds and transient failures have up to three attempts. Retry-After deadlines persist. Media transfers start at one or two concurrent files and grow after successful network transfers within device and connection limits, up to eight for Posts and four for Discord. Missing hardware hints retain a ceiling of two. HTTP 429 immediately reduces concurrency and blocks new starts until the retry deadline, including the tick that observes the response; repeated network/server failures reduce concurrency too. A persisted cooldown prevents immediate increases. Capacity reductions let already running transfers finish. Discovery request pacing is unchanged. Pause/cancel aborts post transfers, and completed staging is reusable. Discord retains its existing image signatures, decoding, dimensions, byte counts, and SHA-256 checks. Post images retain byte format validation and decoding where supported; arbitrary files are checked for successful stream completion and byte count.

Filenames and path segments are sanitized for Windows. Discord retains `ArchiveRoot`; posts are contained in a single `platform_creatorId_creatorName` wrapper with quality folders and JSON files beneath it. New folder destinations create that wrapper inside the chosen save location; existing creator archives are reused for sync. New post ZIPs use the same wrapper. Paths cannot traverse outside the selected directory. Per-post attachment ordinals prevent filename collisions; an existing different file receives a suffixed new sibling. ZIP64 packaging streams staged files without loading the whole archive into memory. One completed ZIP requests one save location. Clearing the local cache never deletes an externally saved archive.

Post sync imports accept the versioned `sync.json` or a legacy post `manifest.json`, limited to one website, creator, and platform. Connecting history or a creator folder preserves the current single-post or selected-profile scope. Only selected posts generate download tasks or appear in a new ZIP's manifest. Explicit empty selections cannot start downloads; selection edits during ongoing work are rejected. Shared sync history retains earlier successful posts and does not broaden a job's selection. Imported paths and file IDs are validated; successful history is checked against local file existence and byte size before skipping transfers. Failed/unavailable tasks never count as successful history. Folder downloads update the index after successful writes and pause on lost access or write failures. The native folder picker and permission requests require a user gesture in a dedicated extension tab; the overlay remains the primary interface.

Storage cleanup is an explicit overlay action. Removing one job or clearing all extension data requires an inline confirmation and stops the affected work. Cleanup removes internal job/history records, imported sync history, unused or all folder connections, blob URLs, and private staging caches. Global cleanup also removes orphan caches. It does not delete downloaded ZIPs, saved archive files, or on-disk sync indexes. Folder handles are forgotten without opening or deleting their target directories.
