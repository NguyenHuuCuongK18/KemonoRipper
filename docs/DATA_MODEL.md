# Data model

Version 0.4 upgrades `kemono-archive` to schema 4. The `jobSummaries` store contains compact titles, source URLs, statuses, timestamps, destination kinds, archive states, and cache-cleared flags. A migration backfills summaries for existing Discord and post jobs, and job writes/deletions update summaries in the same transaction. Full normalized post/task/media histories remain in their original stores. New archive-download-ID indexes, a media-download-ID index, a composite media job/status index, and a manifest-state index support targeted completion and recovery. ZIP completion updates staged records and the job atomically without replacing unrelated media.

Cache settings add `clearAfterDownload`, default false, while retaining the 5-minute idle default. Saved archives may carry `cacheCleared: true`; this distinguishes a successful download whose private staging/ZIP data has been removed from one available for another local export. Saved counts and downloaded task/media records remain intact. `cacheCleanupError` records a retryable cleanup problem without changing a successful download into a failure. New exports validate existing caches and refetch missing bytes; retry also requeues successes when the old cache was cleared. Removing an unsaved cache resets its export state while preserving discovered source metadata. No cache command deletes a chosen folder or browser download.

Version 0.3.6 upgrades `kemono-archive` to schema 3, adding `status` and `archiveState` indexes and a `settings` store. Existing records are retained. Cache maintenance stores `retentionMinutes` (default 5, 0 disables cleanup), `lastCheckAt`, and the number of caches removed by the last check. Private ZIP directories contain a `.last-used` timestamp, refreshed on actual file use and persisted at most once per 15 seconds. Legacy caches use their job update time and file modification dates. Cleanup removes only expired private caches; ongoing and paused jobs are protected. Expired ZIP jobs retain discovery metadata and can download again; chosen folder connections and sync history are retained.

`src/core/types.ts` defines jobs, channel checkpoints and normalized media records. Discord IDs are strings throughout. Media identities combine server, channel, message, attachment ordinal and a stable token of the verified storage path or explicitly observed source URL. Repeated filenames and repeated attachments retain distinct ordinals. Records are scoped to jobs; new jobs do not automatically reuse completed downloads from older jobs.

Each IndexedDB `media` key is `[jobId, id]`, with a `jobId` index. Page checkpoints retain offsets, page fingerprints, unique message IDs, terminal conditions, errors, retry history and retry times. A single transaction replaces a job's merged media and commits its next checkpoint. A failed transaction cannot silently skip a page.

Records retain raw and UTC publication time, API/DOM provenance, available candidate URLs, unsupported or temporary identity warnings, selected quality, transfer attempts, browser download IDs, saved relative path, actual MIME/size/dimensions and downloaded-content SHA-256. The Kemono original-file hash is stored separately. Attachment IDs and Discord CDN URLs remain null unless present in genuine source data.

Statuses distinguish metadata discovery, queuing, in-flight transfer, successful file saving, failure and skipped items. Job coverage and downloaded-file availability are distinct; exported totals flag incomplete channels and unresolved/failed/skipped transfers. Manifests exclude internal blob URLs and local absolute download paths.

Version 0.1.1 adds optional job scope, canonical source URL, discovered-channel count, and API/DOM channel-discovery provenance. Existing jobs remain readable without an IndexedDB schema migration. Canonical source URLs exclude arbitrary query/fragment values. An entire-server job discovered only from visible DOM links remains potentially incomplete, even after all those visible channels are scanned successfully.

Version 0.1.2 adds an optional destination (`folder` with a display name and immutable directory ID, or `browser`), folder-access error, and saved manifest paths. Directory handles live in the separate `kemono-archive-destinations` database; handles and absolute paths never enter runtime messages or manifests. A new selection gets a new directory ID. Switching an existing job to a folder verifies completed files there by size and checksum, requeues missing files, and atomically commits the job and media updates. Existing jobs can still be paused, resumed or migrated without rescanning metadata.

Version 0.1.3 adds the default `zip` destination, a `staged` media status and a staged summary count. ZIP state is pending, building, ready, saving, saved or failed, with filename, entry counts, byte count, packaging progress and final browser download intent. Staged files become downloaded atomically only after ZIP completion. Internal archive blob URLs are excluded from manifests. OPFS cache names derive from validated job IDs and SHA-256 media IDs; the public ZIP retains deterministic channel/filename paths.

Version 0.3 adds optional `destination`, `sync`, and pending automatic-download selection to post jobs in the existing `postJobs` store. Older post jobs without a destination retain ZIP behavior. `sync.json` has format `archive-ripper-post-sync`, version 1, source origin/platform/creator ID, creator name, update time, selection, and a `posts` array. Each downloaded post holds its ID/title and successful file records with stable task ID, quality, kind, creator-relative path, and byte count. No native handles, absolute paths, or temporary blob URLs appear in it. Failed/unavailable tasks remain in `failures.json`, not successful history. A post can contain partial successful history; sync skips individual verified files so partial failures and expanded content selections remain recoverable. Verification uses file size, not content hashes. Modified text in an already saved post is retained; sync discovers new posts and missing/newly selected attachments rather than replacing local edits.
