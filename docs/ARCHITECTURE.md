# Architecture

`services/registry.ts` recognizes supported sites and routes Discord URLs separately from Patreon/Fanbox profile and post URLs. `services/router.ts` dispatches typed runtime commands. The service worker serializes state changes and schedules one active archive service at a time; starting another service pauses the current job.

Version 0.4 separates read-only status/history/cache commands from the mutation queue so a slow scan request does not block progress reads. `background/scheduler.ts` coalesces wakeups, prevents overlapping ticks, honors requested delays, and stops its fast timer when the indexed summary store reports no active job. Commands and alarms wake the worker; nonterminal browser download updates do not enqueue reconciliation. Completion and recovery use download-ID, media-status, archive-state and manifest-state indexes instead of reading every completed job's media. Discord ticks reuse their in-memory record changes rather than fetching the full media set three times.

Compact job summaries are written transactionally alongside full records and backfilled on database upgrade. Recent history and periodic maintenance read those summaries. UI progress DTOs omit post scan fingerprints/detail queues and, on request, Discord media/message-ID arrays; aggregate counts are computed in one pass. The UI uses one adaptive refresh timer, pauses it when hidden, and keeps unchanged post rows in place.

`services/cacheMaintenance.ts` manages inspection and individual removal across both services and orphan caches. Offscreen inspection reads file metadata and the activity marker without touching idle timestamps or reading attachments. Removal validates private cache IDs and protects ongoing/paused work. An optional after-download policy clears private copies only after a successful browser completion is persisted. Successful history remains saved with an explicit cache-cleared flag; cleanup failures retain success and are retried. Existing idle expiry remains available independently.

`services/discord` exposes the existing Discord engine. Its API/DOM normalization, independent channel checkpoints, bounded retries, image validation, ZIP/folder/browser destinations, and recovery remain available. New jobs carry a Discord service tag so their output goes under `ArchiveRoot/discord`. Untagged older jobs preserve their original paths.

`services/posts` contains the post API client, normalizer, selection and path rules, durable controller, streaming transfers, and ZIP entry generator. Profile pagination steps by 50 and stops only at a validated empty array. Repeated pages and failed requests never silently count as complete. API records requiring post detail are hydrated before discovery completes. A post URL fetches only that post and creator metadata.

IndexedDB version 2 adds a `postJobs` store without replacing the existing `jobs` or `media` stores. A post job persists normalized posts, options, pagination, retry deadlines, per-file tasks, and ZIP state. Creator/post IDs stay strings. Commands validate origins, service names, creator ownership, post identity, selections, and attachment paths.

The offscreen document owns long transfers so the worker can continue answering pause/cancel/status commands. It streams responses directly to OPFS and validates completed transfers. `core/transferConcurrency.ts` bounds simultaneous transfers using half the browser-reported logical processors, approximate GiB of RAM, and connection hints, with a maximum of eight for Posts and four for Discord's buffered images. Missing CPU or RAM hints cap concurrency at two; Data Saver and 2G cap it at one and 3G at two. Jobs start with at most two transfers and add one slot after twice the current limit in successful network transfers. Text generation does not grow the pool. HTTP 429 halves the limit immediately; two transient failures also halve it. A minimum 30-second cooldown (extended by Retry-After) prevents completed in-flight transfers from immediately undoing the reduction. Optional per-job policy fields persist without a database migration. Each scheduling pass clamps to current device hints and accounts for existing active transfers; a lower ceiling drains active work without aborting it. Post scheduling rechecks a newly received rate-limit deadline before starting anything in that tick. API discovery retains its existing pacing. More options shows the current transfer limit.

Pausing or cancelling aborts active post transfers. Worker restarts poll existing offscreen transfers or safely queue interrupted tasks again. Disk-backed staging is shared with Discord; `zipCache.createArchive` streams arbitrary validated entries through zip.js ZIP64. This increases concurrent network transfers rather than creating extra extension service workers. Browser hardware reports are capacity hints, not measurements of currently free resources or a guaranteed worker limit ([HTML concurrency specification](https://html.spec.whatwg.org/multipage/workers.html#navigator.hardwareconcurrency), [Device Memory specification](https://www.w3.org/TR/device-memory/)).

Post task identities include the post, quality, and attachment identity. Qualities have separate `thumbnail` and `full res` trees beneath the platform and creator. Version 0.3.5 creates post directories as `YYYY-MM-DD_postId_title` using the UTC publication date (`unknown-date` if invalid or absent). Path validation and sync import accept both dated and legacy `postId_title` directories; verified saved files keep their existing paths. Non-image files are included only for full resolution. Text is converted in an inert document to a separate UTF-8 `post.txt`. Each ZIP includes a manifest and failure report.

The Posts UI selects full resolution with an optional `fallbackToThumbnail` checkbox, checked for new jobs. Legacy selections remain readable and absent fallback flags preserve their old behavior. Missing metadata or HTTP 404/410 can replace an image task with a thumbnail task, changing its ID, quality, URL, and path together. Its reason is retained on the task and the original offscreen transfer ID is forgotten. Folder fallbacks are checked against saved thumbnail history before transfer; later syncs still attempt available originals. Rate limits, network errors, and server errors retain the original retry policy. Fallbacks never apply to arbitrary files or post text.

Version 0.3 adds creator-folder destinations and portable post sync indexes. `posts/sync.ts` validates one origin/platform/creator, successful file records, content selection, and quality/post-relative paths. Sync identities remove the attachment ordinal, retaining post, quality, and storage path so reordered attachment arrays do not cause another download. Legacy post manifests are converted from staged/downloaded entries only. The offscreen document verifies files in the selected folder by path and size before skipping them; a JSON alone does not prove the local file exists.

`posts/folder.ts` copies validated staged files into a durable user-selected directory handle. The controller marks them downloaded only after the file writer closes, persists the job, and updates `sync.json` after each successful file. Completed staging files are then removed. Interrupted index writes pause safely and can be flushed again on resume. Sync rescans all creator pages, merges previous history, retries missing files, and preserves unselected qualities. Version 0.3.1 uses `posts/destination.ts` to create a single `platform_creatorId_creatorName` wrapper at a chosen save location, with `thumbnail`, `full res`, and JSON files inside it. A selected existing archive, identified by its validated sync/manifest JSON or quality folders, is reused. Version 0.3.2 normalizes all post ZIP paths, including older job tasks, to that single wrapper. Media, manifest, failure report, and portable sync JSON agree on the layout. Saving an older cached ZIP schedules repackaging from staged bytes; task IDs remain unchanged, so no transfer is needed. Discord keeps its established layout.

The native directory picker lives in a small top-level extension tab because the embedded overlay cannot invoke it. Handles are stored directly in IndexedDB and never sent in runtime messages. The router permits only this extension-owned picker page in addition to supported site tabs. Regranting folder access is a user-gesture operation; background writes never trigger permission prompts.

Version 0.4.1 retains this top-level tab after granting access so closing it cannot immediately end a session-only grant. The return button focuses its opener without closing the access tab. Restoring access commits the granted handle, asks the offscreen writer to validate it, and then resumes a paused job through the serialized router. Reselecting the same directory uses `isSameEntry` and retains its key, staged tasks, options, and pending automatic sync. Resume checks writer access before clearing the paused state, and the overlay clears a resolved permission notice when it refreshes.

Version 0.4.2 lets users connect an existing archive by selecting its `sync.json` or legacy `manifest.json`. `posts/syncDestination.ts` validates the file before any job changes. Existing write access is reused only when the saved directory resolves that exact file as a direct child. Otherwise, a second user gesture opens a directory picker with `startIn` set to the selected file, and direct-child identity is verified before storing the connection. `POST_SYNC_CONNECT` rereads history in the offscreen writer, connects the directory, and starts a creator scan in one serialized mutation. A paused download on the same directory retains tasks and pending automatic sync and resumes through the existing recovery flow. File handles remain transient in the access tab; no schema change or native path is needed. Cancellation and incorrect file/folder selection do not import history or reset work.

The toolbar action is enabled only on the two archive sites. A content script mounts an isolated iframe inside a shadow-root overlay. The extension iframe reads page context through the worker and content script, auto-selects the appropriate service/scope, and resumes an existing matching job or starts discovery. UI progress combines numerator/denominator counts; post rows and recent jobs stay collapsed. Packaging and final browser-save completion share the same progress display. The only browser download for a new ZIP job is the completed ZIP.

`services/localData.ts` handles confirmed `LOCAL_CLEAR` commands through the serialized worker router. It stops affected jobs, cancels their in-progress browser downloads, and asks the offscreen document to abort and await transfers and ZIP builds before deleting private staging. Per-job removal retains folder connections referenced by another job. Global cleanup clears all job/media stores and saved directory handles, revokes blob URLs, and removes only the `kemono-zip-jobs` OPFS namespace, including orphan caches. It never traverses a user-selected archive folder or deletes a downloaded file. Cleanup failures retain stopped job records so the user can retry. The UI clears its selection after removal and offers an explicit new scan; another open view detects a removed job without recreating it during polling.
